# 实验室信息管理系统 SDD 开发流程

> SDD（Spec-Driven Development，规范驱动开发）是本项目的统一开发流程。所有编码工作都必须从已确认的 Spec 出发，并通过计划、任务、实现、审查和验证形成闭环。

## 1. 核心原则

1. Spec 是系统行为的唯一事实源，当前入口是 `specs/001-lims-core/spec.md`。
2. 技术调研产生决策依据，不能直接替代需求。
3. 需求、设计、任务、代码和测试必须使用稳定 ID 进行追踪。
4. Plan 和 Tasks 是 Spec 的派生物，不能偷偷扩大功能范围。
5. 任何功能先定义验收条件，再进入实现。
6. 每个阶段都有进入条件、退出条件和质量门禁。
7. 并行工作只能发生在依赖明确、文件边界清晰的任务之间。
8. 对抗性审查必须主动寻找遗漏、越权、异常、并发、恢复和维护风险。
9. 版本化保存需求、数据库迁移、API 契约和测试结果。
10. 优先采用模块化、配置化和可替换设计，避免过早绑定具体实现。
11. 本项目开发、联调、迁移验证、演示和验收使用经授权的远程 Supabase；远程 Dashboard 的人工操作通过受控浏览器执行，自动化操作必须可重复、范围明确并留存证据。
12. 开始需求、设计或编码前必须完成规范读取准入，具体检查项见[远程 Supabase 工作流](remote-supabase-workflow.md)。

```text

├─ constitution.md                 # 项目级治理原则
├─ product.md                      # 产品级目标与边界
└─ 001-lims-core/

   ├─ design.md                    # 分析模型
   ├─ architecture.md              # 架构与技术决策
   ├─ data-model.md                # 数据详细设计
   ├─ ui.md                        # 页面和导航
   ├─ api-contract.md              # API 人读契约
   ├─ contracts/openapi.yaml       # API 机器可读契约
   ├─ plan.md                      # 实现计划
   ├─ tasks.md                     # 实现任务
   └─ traceability.md              # 需求追踪矩阵

docs/
├─ kb/                             # 技术调研与参考资料
├─ prd/                            # 产品简报视图

├─ task/                           # 毕业设计宏观阶段计划
└─ sdd/                            # SDD 流程、模板和质量规则
```

## 3. 标准开发循环

```text
技术调研
  ↓
需求澄清与 Spec 更新
  ↓
技术设计与 ADR
  ↓
任务分解与依赖分析
  ↓
并行实现与集成
  ↓
对抗性审查
  ↓
自动化测试与质量门禁
  ↓
一致性检查
  ↓
版本发布与知识回填
```

每个新功能都按同一循环执行，不直接从一句自然语言需求跳到代码。

远程数据库和开发准入的统一约束见：[远程 Supabase 工作流](remote-supabase-workflow.md)。

## 4. 阶段、输入、产物和门禁

| 阶段 | 主要工作 | 必备产物 | 退出条件 |
| --- | --- | --- | --- |
| S0 初始化 | 建立 Spec、规则和工作区 | `AGENTS.md`、`specs/README.md`、`constitution.md` | 所有人知道唯一事实源 |
| S1 技术调研 | 调研方案、风险、成本和可替代项 | `docs/kb/*`、ADR 草稿 | 关键技术选择有来源和结论 |
| S2 需求管理 | 澄清目标、用户、流程、边界和验收 | `spec.md`、变更记录 | 需求有 ID、状态和验收条件 |
| S3 技术设计 | 架构、数据、API、页面、安全和迁移设计 | `design.md`、`architecture.md`、`data-model.md`、`api-contract.md` | 设计覆盖所有 Approved 需求 |
| S4 任务分解 | 拆分任务、标记依赖、估算风险和并行性 | `plan.md`、`tasks.md` | 每个任务可独立验收 |
| S5 开发编码 | 按任务实现、测试、提交和回填 | 代码、测试、migration、文档 | 任务对应代码和测试 |
| S6 对抗性审查 | 主动攻击需求、设计和实现 | 审查记录、问题清单 | P0/P1 问题关闭或获批准豁免 |
| S7 质量控制 | 自动检查、测试、手工验收和回归 | 测试报告、质量门禁记录 | 所有强制门禁通过 |
| S8 一致性对齐 | 检查 Spec、设计、任务、代码和测试 | 追踪矩阵、检查结果 | 无断链、无重复事实源 |
| S9 版本发布 | 版本、变更说明、部署和回滚 | CHANGELOG、版本标签、发布记录 | 可复现、可回滚、可说明 |

## 5. 技术调研流程

### 5.1 调研问题

每次调研先写清楚：

- 要解决什么技术问题。
- 影响哪些需求 ID。
- 候选方案有哪些。
- 评价维度是什么：学习成本、功能覆盖、维护成本、可替换性、部署风险和安全风险。
- 哪些结论需要官方文档、标准或可运行验证支持。

### 5.2 调研产物

使用 [技术调研模板](templates/research-template.md)，至少记录：

- 问题和背景。
- 候选方案。
- 证据和来源。
- 实验或 PoC 结果。
- 风险与退出方案。
- 最终决策和影响范围。

调研不直接修改需求。若调研导致范围或约束变化，必须创建变更记录并更新 Spec。

## 6. 需求管理流程

需求必须遵循：

```text
Draft → Proposed → Approved → Implemented → Verified
                         ↘ Deprecated / Rejected
```

每条需求至少包含：

- 唯一 ID。
- 角色和触发条件。
- 可验证的系统行为。
- 异常和边界条件。
- 验收条件。
- 优先级、状态和来源。

需求变更必须说明影响的设计、任务、代码、测试和论文材料。

## 7. 技术设计流程

设计顺序固定为：

1. 系统边界和上下文。
2. 模块边界和依赖。
3. 数据模型和约束。
4. API 契约和错误模型。
5. 页面、交互和权限。
6. 安全、日志、备份和恢复。
7. 部署、迁移和回滚。

技术选型和不可逆决定使用 ADR 记录，设计不能只存在于聊天记录或代码中。

## 8. 任务分解规则

一个任务应该满足：

- 一个明确结果。
- 一个主要责任模块。
- 一个或多个 Spec/验收 ID。
- 明确输入、输出和依赖。
- 能在一次工作会话中完成或继续交接。
- 有测试或检查方法。

任务格式：

```text
T-xxx [P?] 动词 + 结果
Spec: FR-xxx / NFR-xxx / AC-xxx
Depends: T-xxx
Files: 预计修改路径
Verify: 测试、检查或演示方式
```

## 9. 开发编码流程

1. 先读取 `specs/README.md`、`specs/constitution.md`、`specs/001-lims-core/spec.md`、相关 Plan/Design/Tasks 和本 SDD 流程；若规范缺失、过期或冲突，先治理规范。
2. 从 `tasks.md` 领取一个已满足依赖的任务。
3. 读取相关 API 和数据模型，先补测试或验收场景，再实现代码。
4. 保持模块边界，不跨模块直接访问内部数据；数据库操作连接经授权的远程 Supabase。
5. 完成后运行局部测试和一致性检查。
6. 更新任务状态、追踪矩阵和必要的技术文档。
7. 使用小而完整的提交，说明需求 ID。
8. 通过对抗性审查后再合并。

## 10. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才能标记完成：

- 需求 ID 明确且未改变语义。
- 代码、配置、migration 或文档已提交。
- 正常流程和至少一个异常流程已验证。
- 权限和审计影响已检查。
- 相关自动化测试通过。
- 没有新增未记录的技术债务。
- 追踪矩阵、任务状态和变更说明已更新。
- 对抗性审查没有未处理的 P0/P1 问题。

## 11. 维护与扩展

- 新模块通过模块目录和明确接口扩展，避免修改核心模块内部细节。
- 外部服务通过适配器隔离，Supabase 访问集中在服务端数据层。
- 数据库变更只通过 migration，禁止手工改线上结构。
- API 保持 `/api/v1` 版本边界，破坏性变更进入新版本。
- 状态、错误码、权限码和枚举集中管理。
- 复杂规则使用策略或配置表扩展，不把业务条件散落到页面组件。
- 任何缓存、Realtime、队列或 AI 能力都必须先有需求和失败降级方案。
