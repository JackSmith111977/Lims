## 现象

执行 `npx supabase db push --linked --yes` 时，Supabase CLI 在 Windows 用户目录写入 telemetry 临时文件失败，错误为 `EPERM`。将 CLI 配置目录重定向到临时目录后，CLI 又因新的配置目录没有登录凭据而返回 `Access token not provided`。

同一时间，Supabase Dashboard 显示技术故障提示。SQL Editor 页面可以加载并显示已登录的 postgres 角色，但在通过浏览器自动填写或运行较长 SQL 时持续超时，未能得到可靠的执行结果。因此本次没有把远程 migration 标记为已应用。

## 已收集证据

- 本地 migration 文件存在且长度完整：`supabase/migrations/202607150012_experiment_processing.sql`。
- 本地 `tsc`、Lint、单元测试、生产构建和未认证 E2E 均通过。
- 失败发生在 CLI 文件系统和认证阶段，尚未得到数据库返回的 SQL 语法错误。
- 未读取、打印或提交任何 access token、service role key 或浏览器登录态。

## 可复现与恢复步骤

优先在已登录 CLI 的终端执行：

```powershell
$env:SUPABASE_CLI_TELEMETRY_DISABLED = "true"
npx.cmd supabase db push --linked --yes
```

如果仍然需要登录，应在本机执行 `npx supabase login`，完成登录后重新运行上面的迁移命令。也可以在 Supabase Dashboard 的 SQL Editor 中一次性执行该 migration 文件内容，但执行后必须通过 migration 目录记录和后续集成测试确认结果。

## 结论

远程状态保持“未验证”比把本地成功误报为云端成功更安全。恢复后应先执行 `202607150012_experiment_processing.sql`，再运行处理模块的远程集成测试，最后关闭 T-303B～E 的任务状态和审查记录。

## 追加证据（2026-07-15）

- 使用临时配置目录执行 `npx.cmd supabase telemetry disable` 成功，说明遥测写入不是不可恢复的 CLI 功能故障。
- 在遥测已关闭后执行 `npx.cmd supabase migration list --linked --output json`，CLI 明确返回 `Access token not provided`；当前本机没有可用于 Supabase CLI 的登录态或 `SUPABASE_ACCESS_TOKEN`。
- 官方 CLI 认证方式是 `supabase login` 使用个人访问令牌，或通过 `SUPABASE_ACCESS_TOKEN` 注入令牌。令牌不得发送给 Codex、写入仓库或写入日志；恢复时应由用户在本机完成登录，再运行迁移和集成脚本。
- 本地已准备 `scripts/integration/experiment-processing.mjs` 和 `scripts/integration/cleanup-experiment-processing.sql`。前者覆盖成功、阈值异常、失败补偿、规则防伪、RLS、不可变边界、任务锁定和审计；后者仅按 `processing_*` 测试前缀清理，并在数据库 owner 的测试 SQL 会话中临时关闭用户触发器以清理不可变测试运行记录。
