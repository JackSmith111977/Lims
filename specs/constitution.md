# Spec 治理原则

## 1. 规格优先

所有实现工作必须能够追溯到一个已确认的 Spec 需求。没有需求 ID 的功能不能直接进入正式实现。

## 2. 单一事实源

系统行为需求只在 `specs/001-lims-core/spec.md` 中定义一次。其他文档通过链接、摘要或映射引用，不复制完整需求正文。

## 3. 产品、需求、设计分层

- 产品层说明目标、用户、价值和范围。
- 需求层说明系统必须提供的可验证行为。
- 设计层说明如何实现需求。
- 任务层说明按什么顺序完成实现。

不同层次不得互相替代，也不得在低层文档中偷偷扩大范围。

## 4. 可验证性

每一条 Approved 功能需求都应有明确的验收条件，能够通过测试、演示、检查或文档审查验证。

## 5. 变更可追踪

需求变更必须同步评估对数据模型、接口、页面、测试、任务和论文内容的影响。需求编号不可复用。

## 6. 适合毕业设计的最小复杂度

优先实现样品—任务—数据—审核—报告的主闭环。仪器直连、复杂智能算法和企业级系统集成属于扩展范围，不能阻塞核心闭环交付。

## 7. 文档状态透明

文档和需求必须标注 Draft、Proposed、Approved、Implemented、Verified 等状态，禁止将草稿内容表述为已确认事实。
