# SDD 对抗性审查手册

对抗性审查的目标不是评价代码风格，而是主动证明“当前需求、设计或实现可能不成立”。审查者应站在攻击者、误操作用户、故障环境和未来维护者的角度提出反例。

## 1. 审查时机

- Spec Approved 前：攻击范围、角色、状态和验收条件。
- Plan Approved 前：攻击技术风险、边界和不可逆决定。
- 合并前：攻击代码、权限、数据一致性、异常和测试缺口。
- 发布前：攻击部署、迁移、备份、恢复和回滚。

## 2. 审查视角

### 需求攻击

- 是否存在没有角色或触发条件的功能？
- 是否存在无法验证的“方便、快速、智能”等模糊词？
- 退回、取消、重复提交、过期和归档路径是否定义？
- 是否把扩展功能误当成 P0？

### 权限攻击

- 实验人员能否读取其他项目的样品和结果？
- 停用用户能否继续调用 API？
- 前端隐藏按钮后，后端是否仍允许越权？
- RLS 与服务端权限结论不一致时谁负责阻断？

### 数据攻击

- 唯一编号是否可重复？
- 并发领用是否可能造成库存为负？
- 审核后的结果是否能被无日志覆盖？
- 删除样品或任务后，报告还能否追溯？
- migration 中断后能否恢复？

### 接口攻击

- 重复提交 POST 是否会产生重复任务或报告？
- 状态冲突是否返回明确错误？
- 分页、排序和筛选是否有上限？
- 附件下载是否验证对象权限？
- 外部服务超时是否有重试和降级行为？

### 运维攻击

- Supabase 不可用时是否有提示和恢复方案？
- 环境变量泄露会造成什么影响？
- 备份是否能真正恢复，而不是只有备份文件？
- 发布失败能否回滚代码和数据库？

### 可维护性攻击

- 新增实验方法是否需要修改多个页面？
- 状态值是否散落在字符串中？
- 业务逻辑是否被复制到多个 Route Handler？
- 更换文件存储或认证服务是否需要重写业务模块？

## 3. 问题等级

- `P0`：阻塞发布、造成数据泄露、越权或不可恢复错误。
- `P1`：核心流程错误、严重数据不一致或重要需求缺失。
- `P2`：一般缺陷、体验问题或维护成本上升。
- `P3`：建议、优化或后续探索。

## 4. 审查记录格式

每个发现至少包含：

- 审查对象和版本。
- 需求/设计/代码/测试 ID。
- 攻击场景。
- 预期行为和实际行为。
- 等级和影响。
- 修复方案、负责人和截止条件。
- 复测结果。
