# 实验室信息管理系统技术栈选型分析

| 项目 | 内容 |
| --- | --- |
| 决策编号 | ADR-002 |
| 当前结论 | Next.js + shadcn/ui + Supabase |
| 备选方案 | Vue + Spring Boot + MySQL |
| 状态 | 已确认，待项目骨架初始化时锁定具体版本 |
| 日期 | 2026-07-11 |

## 1. 选型背景

项目当前尚未开始编码，开发者可以现学技术，目标是完成一个功能完整、界面可演示、数据关系清晰的高校科研实验室信息管理系统。因此优先考虑：

- 减少基础设施搭建工作。
- 快速完成管理后台页面。
- 保留规范的业务分层、权限和数据追溯能力。
- 适合 AI 协作和毕业设计文档说明。

## 2. 方案对比

| 维度 | Vue + Spring Boot + MySQL | Next.js + shadcn/ui + Supabase |
| --- | --- | --- |
| 前后端边界 | 清晰，传统分层明显 | 可在一个全栈项目中组织 |
| 开发速度 | 需要搭建独立后端、认证和文件服务 | BaaS 提供认证、数据库和存储 |
| 管理后台 UI | 组件较完整，开箱即用 | 源码可控，需自行组合表格和表单 |
| 数据库控制 | 自主部署、迁移路径清晰 | PostgreSQL 托管，需管理 RLS 和迁移 |
| 权限实现 | Spring Security 中央控制 | Supabase Auth + RLS + 服务端授权 |
| 学习成本 | Java、Spring、前后端分离 | React、Next.js、RLS、Supabase |
| 毕设展示 | 更突出后端工程能力 | 更突出全栈交付、界面和快速迭代 |
| 外部依赖 | 较少 | 依赖 Supabase 服务，需要保留迁移和备份方案 |

## 3. 最终决策

本项目采用：

```text
Next.js App Router
  + TypeScript
  + shadcn/ui + Tailwind CSS
  + Supabase Auth
  + Supabase PostgreSQL
  + Supabase Storage
  + Next.js Route Handlers
  + REST/JSON + OpenAPI
```

### 3.1 关键约束

- 页面不能直接散落数据库访问逻辑。
- 业务规则集中在 `modules/` 服务层。
- 所有业务表启用 Supabase RLS。
- 关键状态变更必须通过服务端函数执行。
- 数据库通过 migration 文件管理，不只依赖云端控制台。
- 继续保留需求 ID、API 契约、审计日志和数据追溯设计。

### 3.2 风险控制

- BaaS 不可用：保留本地 Supabase CLI 和数据库 migration。
- 平台迁移：业务表使用标准 PostgreSQL 结构，附件保存对象元数据。
- 权限错误：同时使用 Route Handler 服务端校验和数据库 RLS。
- UI 组装复杂：优先使用 shadcn/ui 已有组件，先完成表格、表单、弹窗、分页和导航。
- Next.js 概念较多：第一版只使用 App Router、Server Components、Client Components 和 Route Handlers，不引入复杂缓存或边缘运行时。
