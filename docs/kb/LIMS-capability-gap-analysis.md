> Thermo Fisher 页面是商业 LIMS 的能力参考，不是本项目的需求清单。本项目仍以 GB/T 分析、核心 Spec 和已批准的单实验室科研场景为准。任何候选项进入开发前，必须经过 Spec → Plan → Tasks → Implement → Verify 流程。

## 1. 分析结论

当前项目已经完成“实验过程管理 + 资源管理 + 系统管理”的核心 MVP 闭环：

```text
用户与权限
  → 项目/任务登记
  → 样品登记与流转
  → 任务分配
  → 数据录入/导入
  → 数据处理
  → 结果审核
  → 报告生成与追溯
  → 统计、审计与归档
```

当前项目尚未达到商业级企业 LIMS 的完整能力，主要差距集中在：

1. 真实仪器、自动化设备和环境传感器接入。
2. 可配置工作流、SOP 和质量管理。
3. 企业系统集成、移动离线采集和跨实验室协作。
4. 法规级电子记录、电子签名、MFA 和完整合规验证。
5. 高级报表、趋势分析、资源排程和预测性维护。

因此，项目当前定位应为：

> 面向高校科研实验室的、以远程 Supabase 为后端的单实验室 LIMS MVP；具备可演示的核心数据闭环和安全边界，但不宣称具备商业产品级自动化或法规合规能力。

### 2.2 当前部分实现或仍需补齐

| 能力 | 当前状态 | 主要差距 |
| --- | --- | --- |
| 修改密码 | 核心 Spec 定义了 `FR-AUTH-007`，但当前没有对应页面和 `/auth/password` 接口 | 用户无法在系统内完成密码修改流程 |
| 样品附件 | 数据库有通用附件结构，但当前实际上传能力主要用于方法附件 | 送样单、照片、样品文件的上传、预览、权限和保留策略不完整 |
| 样品提醒 | 已有样品状态和流转 | 尚未形成待处理、异常、临近处置的独立提醒机制 |
| 任务资源关联 | 任务支持人员/实验组分配，库存交易已有任务关联边界 | 设备和试剂耗材的统一分配、占用、释放和冲突检查不完整 |
| 报告文件 | 当前提供不可变 JSON 导出 | 尚未提供 PDF/Word/打印版模板和正式报告文件归档 |
| 电子签名 | 已实现报告快照 SHA-256 签名回执 | 不等于 CA/HSM、证书、时间戳和法律效力意义上的正式电子签名 |
| 备份恢复 | 已有托管备份、逻辑备份、恢复和演练文档 | 不是应用内自动备份平台，也未形成完整自动化灾备环境 |
| UI 最终验收 | 功能和未认证 E2E 已通过 | 登录态最终截图和二次视觉对抗检查仍对应 `T-615/T-616` |

## 3. 与 Thermo Fisher 参考能力的对照

Thermo Fisher 页面将商业 LIMS 能力归纳为样本管理、实验室自动化、仪器管理、移动 LIMS、库存管理、协作环境、实验室管理、仪表板与数据可视化、SOP 合规、企业集成、法规符合性、报告与数据分析、工作流程、云端/本地部署、数据稳固性和数据存档等方向。

| 参考能力 | 当前项目对照 | 状态 |
| --- | --- | --- |
| 样本管理 | 有登记、编号、流转、状态和追溯；附件和提醒不完整 | 部分实现 |
| 实验室自动化 | 有 CSV/XLSX 和模拟接口，没有真实自动化工作站 | 未实现真实能力 |
| 仪器管理 | 有档案、维护、校准和提醒 | 基础实现 |
| 移动 LIMS | 只有响应式 Web 页面，没有离线移动采集 | 未实现 |
| 库存管理 | 有库存、有效期和低库存提醒 | 基础实现 |
| 协作工作环境 | 支持角色权限和共享数据 | 单实验室基础实现 |
| 实验室管理 | 有资源页面、任务和看板 | 缺少排程、周转时间和资源优化 |
| 仪表板与可视化 | 有统计卡片、筛选和异常/库存摘要 | 基础实现，缺少高级趋势分析 |
| SOP 合规 | 没有受控 SOP、版本、培训和强制步骤 | 未实现 |
| 企业集成 | 没有 MES、ERP、ELN、CDS、CRM、OA 对接 | 未实现 |
| 法规符合性 | 有认证、RLS、审计、不可变记录和签名哈希 | 部分实现，不宣称法规合规 |
| 报告与数据分析 | 有报告快照、版本、状态、追溯和 JSON 导出 | 基础实现 |
| 工作流程 | 有固定任务/审核/报告状态机 | 部分实现，缺少图形化配置 |
| 云端或本地部署 | 当前依赖远程 Supabase 和 Next.js | 云端路径实现，本地/混合部署未验证 |
| 数据稳固性 | 有权限、审计和服务端字段保护 | 缺少 MFA、完整身份集成和高级密钥治理 |
| 数据存档 | 有报告归档、审计和备份恢复方案 | 基础实现，缺少法规级保留策略 |

## 4. 难度与风险分级

### 4.1 已完成但技术难度较高

| 主题 | 难点 |
| --- | --- |
| RBAC、RLS 和审计 | 页面隐藏不等于安全，必须同时约束 API、RPC、RLS 和审计字段 |
| 样品/任务状态机 | 需要处理并发、非法流转、操作人、时间、交接和历史一致性 |
| 数据处理和血缘 | 原始数据不可篡改，规则版本、运行状态、输出结果和异常需要关联 |
| 报告快照和版本 | 报告生成时必须固定任务、样品、数据和模板内容，并保证状态转换一致 |
| 库存事务 | 余额不能由客户端直接修改，需处理并发扣减、库存不足和不可变流水 |

### 4.2 下一阶段最难的未实现能力

| 优先级 | 能力 | 难度 | 原因 |
| --- | --- | --- | --- |
| 1 | 真实仪器和环境传感器接入 | 极高 | 协议、设备身份、网络异常、离线缓存、幂等、时间同步和数据校准 |
| 2 | 法规级电子签名和合规 | 极高 | CA/HSM、证书、时间戳、不可抵赖、审计和验证材料 |
| 3 | 可配置工作流和 SOP | 高 | 流程版本、权限矩阵、并发修改、回滚和历史兼容 |
| 4 | ERP/MES/ELN/CDS 等集成 | 高 | 字段映射、身份认证、重试、幂等、消息监控和跨系统一致性 |
| 5 | 移动离线采集 | 高 | 本地缓存、冲突解决、重新同步、设备能力和数据安全 |
| 6 | PDF/Word 报告和文件归档 | 中高 | 模板、版本、权限、签名、存储、下载、打印和长期保留 |
| 7 | 自动排程和资源优化 | 中高 | 设备、人员、耗材、优先级、周期、冲突和重新分配算法 |
| 8 | 高级趋势分析和预测维护 | 中高 | 需要稳定历史数据、指标体系、模型验证和异常解释 |

## 5. 下一阶段建议路线图

### 阶段 0：MVP 收口

目标：把当前系统从“核心功能可用”提升为“基本可交付”。

建议内容：

1. 完成 `FR-AUTH-007` 修改密码。
2. 补充样品附件和样品处理/异常提醒。
3. 完成任务与设备、耗材的统一资源关联。
4. 增加 PDF 或可打印报告输出。
5. 完成 `T-615/T-616` 登录态视觉验收。
6. 补充真实账号、迁移、管理员初始化和回滚演练说明。

退出条件：核心 P0 全部通过，P1 遗留项有明确状态，普通用户可以完成一次完整业务闭环。

### 阶段 1：实验室可用性增强

目标：提高日常操作效率和数据完整性。

建议内容：

- SOP 文件和版本管理。
- 样品/任务/报告附件统一管理。
- 任务资源占用、释放和冲突提示。
- 设备预约、维护窗口和任务排程。
- 更完整的报告模板、打印和导出。
- 低库存提醒扩展为采购建议，但不自动下单。

退出条件：实验人员可以按照 SOP 完成任务，管理员可以看到资源冲突、样品附件和报告文件。

### 阶段 2：自动化与接口试点

目标：从模拟数据过渡到可控的真实接口试点。

建议内容：

- 先选择一种设备和一种协议，不同时接入多家厂商。
- 建立设备适配器、数据映射、来源校验和幂等键。
- 增加接口运行状态、失败重试和人工补录。
- 选择一种环境传感器，验证温湿度采集和超限提醒。
- 保留 CSV/XLSX 作为接口失败时的降级路径。

退出条件：单一设备在隔离环境中连续运行，数据可追踪、可重试、可审计，且不会绕过现有数据约束。

### 阶段 3：合规与企业集成

目标：面向正式组织使用，而不是只面向毕业设计演示。

建议内容：

- MFA、组织身份集成和密钥轮换。
- 正式电子签名方案评估和供应商选择。
- 电子记录保留、归档、导出和销毁策略。
- 选择一个外部系统做单向集成试点。
- 建立审计证据、灾备演练、RPO/RTO 和发布审批流程。

退出条件：合规边界、责任主体、审计证据和灾备指标经过组织确认；不得仅凭代码测试宣称满足法规。

### 阶段 4：移动与智能化

目标：提高复杂实验场景下的采集和决策效率。

建议内容：

- 移动端或 PWA。
- 条码/二维码扫描。
- 离线采集和冲突合并。
- 运营趋势分析、周转时间分析和资源利用率。
- 预测性维护和异常预测。

退出条件：模型有稳定数据来源、明确指标、可解释输出和人工兜底，不能直接自动改变关键实验结论。

## 6. 暂不建议立即开发的内容

以下内容容易扩大范围，当前不应直接进入实现：

- 同时接入多个真实仪器厂商。
- 直接开发完整 ERP/MES/ELN/CDS 集成平台。
- 在没有合规责任主体的情况下宣称 21 CFR Part 11 或 ISO 17025 合规。
- 在没有稳定历史数据的情况下开发预测模型。
- 直接做跨组织多租户。
- 先做移动端而不先补齐桌面端的附件、报告和资源关联。

## 7. 下一阶段立项前需要确认的问题

1. 项目继续定位为高校科研实验室，还是转向检测/生产实验室？
2. 是否需要客户/委托方角色和送检流程？
3. 下一阶段优先选择哪一种真实仪器或传感器？
4. 报告输出目标是 JSON、打印 HTML、PDF 还是正式模板文件？
5. 是否有 SOP、ISO 17025、GMP 或 21 CFR Part 11 的正式验收要求？
6. 是否需要移动端和扫码采集？
7. 是否需要和学校已有系统集成？
8. 是否有可用于排程和预测的历史数据？
9. 正式环境的备份、恢复、保留期限和责任人由谁负责？
10. 哪些候选项应进入核心 Spec，哪些只保留在论文展望？

## 8. 进入正式开发的规则

本文件中的“建议”“候选”和“阶段”不是已批准需求。确定下一阶段范围后，应按以下顺序落地：

1. 在 `specs/001-lims-core/spec.md` 新增或变更需求 ID。
2. 更新相关设计文件、数据模型和 API 契约。
3. 在 `plan.md`、`tasks.md` 和 `traceability.md` 中建立映射。
4. 先补验收条件和失败场景，再编码。
5. 完成对抗性审查、质量门禁和一致性检查。
6. 只有在证据充分时，才将候选项标记为 Implemented 或 Verified。
