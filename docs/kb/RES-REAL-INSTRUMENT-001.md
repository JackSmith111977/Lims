## 问题

在保持实验数据、环境记录和审计不可变边界的前提下，评估真实仪器通信/控制和环境传感器自动采集应放在哪一层，以及当前 LIMS 是否应直接承担长连接、设备协议和凭据管理。

## 背景和约束

- `FR-EQUIP-007` 和 `FR-ENV-006` 是 P2 需求；当前任务只要求评估，不要求在本切片内接入具体厂商或真实设备。
- 当前仪器档案把设备状态、校准、维护和实验数据引用作为核心职责；真实通信在 `DES-INSTRUMENT-REGISTRY-001` 中明确留给 T-605。
- 当前环境模型已经支持阈值快照、追加记录、`SENSOR`/`API` 来源预留和同事务审计；真实传感器驱动不应绕过 `record_environment_reading`。
- 现有模拟仪器接口和 CSV/XLSX 导入可作为协议无关的业务边界测试；客户端不能直接写入实验数据或环境记录。

## 候选方案

| 方案 | 优点 | 缺点 | 风险 | 可替代性 |
| --- | --- | --- | --- | --- |
| A. Next.js/Supabase 直接轮询或控制设备 | 部署组件少，页面可快速看到数据 | 长连接、重试、协议驱动和设备凭据进入 Web 请求生命周期 | 请求超时、设备阻塞、密钥暴露、重试造成重复记录 | 低 |
| B. 独立连接器/边缘网关推送标准化读数 | 将厂商协议、断线重连、缓冲和凭据隔离；LIMS 只处理已验证业务事件 | 需要部署连接器、设备映射和运行监控 | 连接器与 LIMS 之间的重复、乱序和时间同步需要治理 | 高 |
| C. 文件落地或厂商 API 批量导入 | 实现成本低，适合无实时要求的设备 | 不是实时通信/控制，错误反馈和幂等处理较弱 | 文件篡改、延迟、重复导入和来源证明不足 | 中 |

## 结论

采用方案 B 作为后续生产集成方向：连接器或边缘网关负责厂商协议、设备认证、断线重连、短期缓冲和标准化；LIMS 提供受权限保护的业务摄取入口，统一写入实验数据或环境记录，并要求 `instrument_id`/实验室、来源类型、采集时间、连接器事件 ID 和原始载荷摘要等可追溯字段。控制命令另设显式权限、确认、超时和审计链路，不与普通数据采集 API 混用。

当前不新增厂商依赖或生产代码。继续使用模拟仪器和文件导入验证业务边界，待明确设备协议、部署位置、凭据托管、实时性、离线缓冲、校准和控制安全要求后，再以独立设计和任务进入实现。

## 退出方案

如果后续只需要离线结果接入，采用方案 C 并复用现有数据导入边界；如果需要实时采集或控制，保留方案 B，禁止把长连接和设备密钥直接放入 Next.js 请求处理器。
